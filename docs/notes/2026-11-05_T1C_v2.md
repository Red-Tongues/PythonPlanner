## 1. Mutable Head + Immutable Seal (G2, G3, G6, G11, G12; replaces T1-C §1) [CFO]

**`packets` stays the live head row:**
- Current field values, status, version, fence/run/lock columns.
- R4's CAS (`UPDATE packets … WHERE version=…`) is unchanged.
- The CFO can read **and edit** it in SQL.

**`field_revisions`** (append-only, triggers block UPDATE/DELETE):
- An AFTER UPDATE trigger on `packets` appends one row per changed field: old/new blob hash, producer, `manifest_hash`, time.
- Edits from the kernel and from the CFO are recorded the same way. A CFO edit is tagged `producer=user_sql` and writes an event.

**`generation_attempts`** (append-only): one row per attempt. Unchanged from T1-C.

**`sealed_bundles`** (append-only):
- Completion writes the canonical JSON snapshot plus its hash.
- Episode number = bundle count + 1. `lifecycle_episodes` is **dropped**.

**`content_blobs(hash, body)`:** large text (prompts, drafts, outputs, eva payloads) is stored once and referenced by hash.

**Re-opening** sets `packets.status` back. Sealed bundles never change.

**Requirement F reworded:**
> Sealed bundles, revisions, attempts, eva passes and events are immutable. A packet's head is editable, and every edit is recorded.

CLAUDE.md Golden Rule 1 needs this wording.

## 2. Validity is intra-packet; everything else is drift (G4, G6; replaces T1-C §2) [CFO]

**Binary manifest:**
- the packet's own upstream stages (prompt → pre-eval → output → post-eval);
- field-definition, preset and contract versions;
- the repo commit for repo-sensitive fields.

The hash is **computed in Python when the revision is written** and stored. Validity is checked in kernel code. There is no recursive SQL and no SQL `sha256()`.

**`drift_risk` (0–10,000)** covers:
- project/objective brief revisions;
- dependency bundles;
- path intersections.

It feeds `refresh_due` only, as in T1 round 3. Reachability and API-change detection are **future inputs** (G13) and are not built in M3a.

## 3. Failure maths (G1, G5, G7, G9; amends T1-C §3)

**Exact formula** (Python arbitrary-precision int, one final division, permutation-invariant):

`A = min(10000, (∏(10000+c_k) − 10000^n) // 10000^(n−1))`

- Recompute it from the attempts every time; never increment.
- PM-verified: (1005, 1005, 1990) gives 4521 in any order. The old step-wise form gives 4521 or 4519.
- Property test: every permutation gives an equal result.

**Unknown cause:**
- counts zero task blame;
- raises an investigation signal that **only affects queue maths, never blocks** [CFO, G5].

**Inheritance:** T1 round 4's automatic bounded prior (`min(1000, old_A // 10)`) [CFO, G7]. Categorical confirmation is deferred.

**Shadow mode + breaker** [CFO, G9]:
- Indicators are advisory until calibrated.
- A hard deterministic breaker stays live: K consecutive failures on the same prompt revision → `needs_review` (status, not deletion). K is versioned config, default 3.

**Thinking (G5):** it is kept for diagnosis and fast reassessment through Juggler. It is redacted, access-controlled and never the sole evidence of correctness.

## 6. GPT-6.1 review of v2 (02:25) — all accepted by the PM
1. **SQL edits vs CAS.**
   - Every semantic edit, including the CFO's, must advance `packets.version`, so an in-flight worker's CAS fails.
   - PostgreSQL: a BEFORE trigger bumps `NEW.version`.
   - SQLite: a guarded version-only update, excluded from the audit column list.
2. **Audit capture vs enrichment.**
   - The trigger captures old/new values and write context atomically.
   - Hashing, blobs and manifest are appended afterwards by the kernel.
   - An **unenriched revision is ineligible** for generation or sealing.
3. **Exact product** uses Python arbitrary-precision ints (signed 64-bit overflows from 5 factors). Store only the bounded result. `A = 0` when n = 0. GPT-6.1 independently confirms 4521 for every permutation.
4. **Sealing.**
   - Episode numbers are allocated under packet-level serialization, with `UNIQUE(packet_id, episode_no)`.
   - The seal is atomic, taken from a version-checked head plus its exact revision/manifest references.
5. **Breaker churn.** Keep the per-revision breaker (K=3), **plus** a linked-lineage retry/resource budget, so cosmetic prompt edits can't reset it. Review/reset authority is explicit.

**Trigger rules:**
- Enumerate the audited semantic columns (status included; version/fence/run/lock excluded).
- Use `UPDATE OF` plus a real change test: SQLite `OLD.x IS NOT NEW.x`, PostgreSQL `IS DISTINCT FROM`.
- The trigger only INSERTs and is the sole revision writer, so there is no recursion path.
- Tests: NULL transitions, no-op assignment, multi-field edits, CAS-only updates, rollback, direct SQL edits.

**New CFO question 7:** if you edit a packet in SQL **while it is running**, should that run be **invalidated immediately** (its result is discarded and the packet re-queues) or should **your edit be refused** until the run ends? *PM view: invalidate. Your edit wins.*
